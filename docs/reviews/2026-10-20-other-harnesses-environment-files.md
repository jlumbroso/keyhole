# Other harnesses: which file holds the environment, in what shape, and when a change applies

- **Date**: 2026-10-20
- **By**: Surveyor 5.1 (Claude Fable 5.1), read only
- **For**: ADR-0001's action item "Read the environment-file conventions of the next harnesses (OpenAI Codex, Google Gemini CLI, xAI Grok)", the three questions a target module must answer: *which file and what shape*, *is it in the project (git-protected) or the home folder*, *how does the value reach the harness's tools and when does a change take effect*
- **Sources**: each vendor's own documentation and source repository, fetched 2026-10-20 by three documentation lookups; quotes are the vendors' wording. Versions: Codex CLI `rust-v0.163.0` (2026-10-15; docs at `learn.chatgpt.com/docs/config-file/…`, undated; source `openai/codex` main); Gemini CLI `v0.64.0` (2026-10-13; `geminicli.com/docs/…`, repo `google-gemini/gemini-cli` main); Grok Build, xAI's official agent, npm `@xai-official/grok` 1.0.62 (2026-10-19 *[corrected below, C3: published 2026-10-16]*; `docs.x.ai/build/…`, undated; the GitHub mirror `xai-org/grok-build` is three weeks behind the binary). Claude Code is in `2026-10-20-adr-0001-source-check.md`, section 3.

## TL;DR

| | Claude Code | OpenAI Codex CLI | Google Gemini CLI | xAI Grok Build |
| --- | --- | --- | --- | --- |
| Harness file that sets variables for the commands the model runs | `.claude/settings.local.json`, `env` object (JSON) | `.codex/config.toml`, `[shell_environment_policy] set = { NAME = "value" }` (TOML); also `~/.codex/config.toml` | **none**; only `.env` files, auto-loaded | `~/.grok/config.toml`, `[shell_environment_policy] set` (TOML), **home folder only** |
| Project `.env` loaded by the harness itself | no | **no** (removed in `rust-v0.30.0`, 2025-09-05); only `~/.codex/.env`, into Codex's own process | **yes**: first `.env` found walking up from the working directory, then `~/.env`; `.gemini/.env` privileged *[corrected below, C2: the walk reaches the filesystem root]* | no; `.envrc` in the working directory, only if `session.load_envrc = true` *[corrected below, C3: on by default, gated by folder trust]* |
| Reaches the shell commands the model runs | yes (Bash, hooks, stdio MCP) | yes, by policy | implied, not stated (the redaction section treats `.env` variables as part of the tool environment) | yes, by policy; `.envrc` "inject into bash" |
| Name-based stripping of secret-looking variables | `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1`, off by default | `ignore_default_excludes = false` drops `*KEY*`, `*SECRET*`, `*TOKEN*`; default `true` (off) | `security.environmentVariableRedaction`, default `false` in the settings list, "automatic" in the prose; `TOKEN`, `SECRET`, `PASSWORD`, `KEY`, `AUTH`, … | `[shell_environment_policy] exclude` patterns; default leaves the environment untouched |
| Project file honored before the folder is trusted | `env` from project files: no, after trust | no: "Codex loads project-scoped config files only when the project is trusted" | no: untrusted folders load neither `.gemini/settings.json` nor any `.env` *[corrected below, C1: a plain `.env` is loaded, four authentication names only]* | project hooks need trust; project config carries no env at all *[C3: `.envrc` loading is also trust-gated]* |
| When a change applies | live for additions and changes; removal at next launch | read at startup; `/config` (0.163) changes some settings live; nothing documented for the policy | startup; no live reload documented for `.env` | "Config is read at session start" |

**What this means for the target-module design** (ADR-0001, the Simon note):

1. **"Which file" has three different answers, and one is "none".** Gemini has no harness file for variables; its target *is* the plain `.env` that keyhole writes first, plus a project `.gemini/.env` that bypasses the exclusion list. Codex and Grok have the same TOML table but in different places: Codex accepts it in the project (`.codex/config.toml`, git-protected, trust-gated), Grok only in the home folder (`~/.grok/config.toml`), outside the project and outside git. The masked box must say which, as the ADR already requires.
2. **The plain `.env` is not a common denominator for reaching commands.** Only Gemini loads a project `.env` into the environment it hands to tools. Under Codex and Grok, a variable in `.env` reaches a command only if that command's own program loads `.env` (a dotenv library, a framework). keyhole's README must say "`.env` is for your program; the harness file is for the model's commands", and not promise more for `.env`.
3. **Every harness can strip a token-named variable from the commands it runs**, by a setting the person may have turned on: Claude Code's scrub, Codex's `ignore_default_excludes = false`, Gemini's redaction, Grok's `exclude`. A harness target should read that setting where it can and say "set, but this harness strips it from commands" rather than let the person debug a missing variable.
4. **Trust gates make "set" and "reaches" two different moments.** In all four, a project-level file is ignored until the folder is trusted. The result line can say "written"; it cannot say "in effect".
5. **Three quoting dialects.** JSON string (Claude), TOML inline-table string (Codex, Grok), shell `export` line (`.envrc`, `.env`). Each target carries its own escaping, which is the first thing a module test must cover.

## 1. OpenAI Codex CLI

- **Files.** TOML. User: `~/.codex/config.toml` (root `CODEX_HOME`, "must already exist" if set). Project: "Codex reads project-scoped overrides from `.codex/config.toml` files inside your repo", walking "from the project root to your current working directory", "the closest file to your working directory wins", and "only when the project is trusted". Profiles as `$CODEX_HOME/<name>.config.toml`; system `/etc/codex/config.toml`; enterprise `requirements.toml` constrains. A project file may not set `model_provider`, `model_providers`, `notify`, `profile`, base URLs and a few more ("should not get to choose where a user's credentials are sent or which local commands are run", `codex-rs/config/src/loader/mod.rs`).
- **The environment for commands.** `[shell_environment_policy]`: `inherit` (`all` default since 2025-08, `core`, `none`), `ignore_default_excludes` ("Keep variables containing KEY, SECRET, or TOKEN before other filters run (default: true)"), `filters` (canonical), `exclude` and `include_only` (legacy), **`set`** ("Explicit environment values injected after exclusions; include filters can still remove them"), `experimental_use_profile`. Order: "automatic exclusions first, then custom exclusions, values from `set`, and finally the include-pattern allowlist". `shell_environment_policy` is not on the project denylist, so `set` works from a trusted project's `.codex/config.toml`; with the credential broker on, the loader strips `ZDOTDIR`, `BASH_ENV` and provider keys from project `set` entries. Two open issues question whether the policy is honored everywhere (#22124, #14774).
- **`.env`.** Project `.env` loading was removed on purpose: PR #3184 "[BREAKING] Stop loading project .env files" ("Loading project local .env often loads settings that break codex cli"). Only `$CODEX_HOME/.env` is read, once, at process start, into Codex's own environment, overwriting, and never for names starting `CODEX_` (`codex-rs/arg0/src/lib.rs`). The documentation does not mention `.env` at all.
- **When.** Startup. `rust-v0.163.0`: "`/config` … change supported settings immediately, and see which changes require a restart"; nothing says the policy reloads. Treat as restart.
- **Its own credentials.** `~/.codex/auth.json` ("treat … like a password") or the OS keyring (`cli_auth_credentials_store`); `CODEX_API_KEY` for non-interactive runs ("Set it inline rather than job-wide when running repository-controlled code"); a bare `OPENAI_API_KEY` is not read by the login code.

## 2. Google Gemini CLI

- **Files.** JSON. `~/.gemini/settings.json`; project `.gemini/settings.json` ("Workspace settings override user settings"); system defaults and system overrides under `/etc/gemini-cli/` or the macOS equivalents. Precedence, low to high: defaults, system defaults, user, project, system settings, **environment variables "potentially loaded from `.env` files"**, command-line flags. In an untrusted folder "the CLI will not load the `.gemini/settings.json` file from the project" and "will not load any `.env` files from the project".
- **No `env` key.** The only `env` object is per MCP server. String values in settings support `$VAR`, `${VAR}` and `${VAR:-default}`, "from your shell environment as well as variables loaded from `.env` files".
- **`.env`, automatic.** "The CLI automatically loads environment variables from an `.env` file": the `.env` in the working directory, else upward "until it finds an `.env` file or reaches the project root (identified by a `.git` folder) or the home directory", else `~/.env`. *[corrected below, C2: that is the documentation's sentence; the code at the same tag stops at neither]* The authentication page adds `.gemini/.env` in the project or home ("Variables are loaded from the first file found, not merged"); the combined order between `.gemini/.env` and `.env` at one level is not documented. `advanced.excludedEnvVars` (default `["DEBUG", "DEBUG_MODE"]`) applies to project `.env` files, "Variables from `.gemini/.env` files are never excluded"; `advanced.ignoreLocalEnv` turns project `.env` off (restart).
- **Reaches commands.** Not stated as a sentence. `run_shell_command` is documented to set `GEMINI_CLI=1`; the redaction section says redaction "applies to variables inherited from the system or loaded from `.env` files" "when executing tools (such as shell commands)", which implies the `.env` variables are in that environment. The prose calls redaction automatic; the settings list says `security.environmentVariableRedaction.enabled` defaults to `false`. Redacted names contain `TOKEN`, `SECRET`, `PASSWORD`, `KEY`, `AUTH`, `CREDENTIAL`, `PRIVATE`, `CERT`; never `PATH`, `HOME`, `USER`, `SHELL`, `TERM`, `LANG`, or `GEMINI_CLI_*`.
- **When.** Settings carry per-key "Requires restart" flags; `.env` loading is described only at load time. Treat as restart.
- **Its own credentials.** `GEMINI_API_KEY` in the shell or in `.env` / `.gemini/.env`; no settings key holds the key.

## 3. xAI Grok Build

- **It exists and is official**: "Grok Build is SpaceXAI's terminal-based AI coding agent", binary `grok`, Rust, `xai-org/grok-build`, `curl -fsSL https://x.ai/cli/install.sh | bash` or `npm i -g @xai-official/grok`. (Two community tools also install a binary named `grok`; `superagent-ai/grok-cli` reads `GROK_API_KEY` from a project `.env` and `~/.grok/user-settings.json`. Not official, and it collides on the name.)
- **Files.** TOML. User `~/.grok/config.toml` (or `$GROK_HOME`). Project `.grok/config.toml` carries only `[mcp_servers]`, `[plugins]`, `[permission]` and one `[mcp]` key: "every other section loads only from `~/.grok/config.toml`". Managed and requirements files; a `GROK_CONFIG` / `GROK_CONFIG_PATH` overlay for harnesses. `grok inspect` shows what was read. The precedence pages disagree on whether environment variables outrank enterprise pins.
- **The environment for commands.** `[shell_environment_policy]`: "controls which environment variables it inherits, so a tool command the model runs cannot read a secret that happens to sit in your shell environment"; keys `inherit` (`all` default), `ignore_default_excludes`, `exclude`, `include_only`, **`set`** ("Inject env values into bash. Not overlay-allowlisted"). Because it is not among the project-loadable sections, **`set` is home-only**.
- **`.env`.** Not loaded; a code search finds `dotenv` only in a sandbox test, and the sandbox examples deny-list `**/.env`. The project-level mechanism is **`.envrc`**: `[session] load_envrc = true  # load .envrc environment variables`, "`direnv export json` when available, else bash with direnv stubs", read from the working directory only, no ancestor walk. Whether those reach Grok's own process or only bash is not documented. *[corrected below, C3: `load_envrc` defaults to `true`; the example line is not an opt-in]*
- **When.** "Config is read at session start, so edit it before starting a session"; some UI keys apply live through `/settings`; hooks reload on request. Treat as restart.
- **Its own credentials.** OAuth session in `~/.grok/auth.json` (mode 0600) or `XAI_API_KEY`; resolution "`api_key` > `env_key` > signed-in session token > `XAI_API_KEY`".

## Doubts worth a sentence in ADR-0001

- **Grok's only project-level route is `.envrc`, which is a shell script**, not a data file: a value written there is executed by bash (or direnv). keyhole's refused-names rule exists because a name can turn a value into code; `.envrc` turns every line into code. If keyhole ever writes it, the quoting is the whole safety, and single quotes with `'\''` escaping are the only safe shape.
- **The documentation lag is real.** Grok's GitHub mirror trails the shipped binary; Codex's in-repo docs are stubs pointing at a site without version stamps. A target module should carry the version it was read against and a "not verified since" date, as keyhole's manual will for VS Code.

## Corrections (2026-10-20, later the same day), pinned to releases

Sounder 6, writing the manual's first chapter, found four places where the vendors' code says more than or differently from the text above. Re-read against pinned releases: Gemini CLI tag `v0.64.0`; Codex CLI tag `rust-v0.163.0`; Grok Build at the public source commit `2bdd1d6a` (2026-09-29) plus the live reference and the npm registry. The lines above that change carry a bracketed marker naming the item here; the original text stays.

### C1. Gemini, untrusted folders: a plain `.env` *is* loaded, four names only, values stripped (changed)

The table said untrusted folders load no `.env`; that is the documentation's sentence, and the code at `v0.64.0` does something narrower. `packages/cli/src/config/settings.ts` L706–716 (https://raw.githubusercontent.com/google-gemini/gemini-cli/v0.64.0/packages/cli/src/config/settings.ts):

```ts
if (!isTrusted) {
  if (!AUTH_ENV_VAR_WHITELIST.includes(key)) { continue; }
  value = sanitizeEnvVar(value);
}
```

with `AUTH_ENV_VAR_WHITELIST = ['GEMINI_API_KEY', 'GOOGLE_API_KEY', 'GOOGLE_CLOUD_PROJECT', 'GOOGLE_CLOUD_LOCATION']` (L91–96) and `sanitizeEnvVar` deleting every character outside `[a-zA-Z0-9\-_./]` (L102–104). In an untrusted folder, `findEnvFile` never considers any `.gemini/.env`, the project's or `~/.gemini/.env` (L569–574, L584–589 are behind `if (isTrusted)`), but a plain `.env` is found and loaded for those four names. An undecided trust (no verdict from the IDE or the trusted-folders file) counts as untrusted (`isTrusted = trustResult.isTrusted ?? false`, L661). Sounder's reading holds.

The companion statement, "`advanced.ignoreLocalEnv` turns project `.env` off", is true but incomplete: with it set, `findEnvFile` still returns a `.gemini/.env` at any level (trusted), a `.env` sitting in the home directory itself (L577, `currentDir === homedir()`), `~/.gemini/.env` (trusted) and `~/.env` (L584–593). It is "no generic `.env` below home", not "no `.env`". Sounder's reading holds.

### C2. Gemini, the upward search: it walks to the filesystem root (changed)

The text above repeats the documentation: the search stops at "the project root (identified by a `.git` folder) or the home directory" (`docs/reference/configuration.md` L2653–2657 at the same tag). The code does not: `findEnvFile` (L561–598) loops until `path.dirname(currentDir) === currentDir`, the filesystem root, with no `.git` test and no home test; only then does it fall back to `~/.gemini/.env` and `~/.env`. At each level the order is `.gemini/.env` (trusted) then `.env`; the first hit wins and exactly one file is loaded. So a `.env` in a parent of the repository, or in the home directory on the way up, is loaded when the project has none. The shipped documentation contradicts its own code at its own tag. Sounder's reading holds.

For keyhole: before keyhole writes a project `.env`, Gemini may have been loading one from an ancestor folder; the probe can say so ("Gemini CLI was loading `<ancestor>/.env`; after this write it loads the project's"), since the first hit changes.

### C3. Grok Build, `session.load_envrc` is on by default, gated by folder trust; and the dates (changed)

The table and section 3 read as if `.envrc` loading were opt-in. It is the default: the live reference row is "`load_envrc` | `[session]` | `true` / `false` (default `true`) | Inject `.envrc` variables into bash" (https://docs.x.ai/build/settings/reference), and the source at `2bdd1d6a` agrees: `SessionConfig.load_envrc: Option<bool>` with the comment "Defaults to `true` when unset" (`crates/codegen/xai-grok-shell/src/agent/config.rs` L1079–1092) and `self.cfg.borrow().session.load_envrc.unwrap_or(true)` at the read site (`src/agent/mvp_agent/session_setup.rs` L1122–1132), where a session-metadata key `x.ai/skip_envrc` can force it off. Two more facts the source adds: the `.envrc` is evaluated only when the folder is trusted (`crates/codegen/xai-grok-workspace/src/envrc.rs` L45–60, `spawn_envrc_load(cwd, trusted)` returns nothing untrusted), and a default `SessionConfig` is saved without the key so a managed `load_envrc = false` is not overridden (`persist_tests.rs` L348). Sounder's reading holds; the row in `26-config-reference.md` has no default column, which is where the opt-in impression came from.

Dates, corrected: `@xai-official/grok` 1.0.62 was published **2026-10-16T16:53Z** (the registry's `time` field); 2026-10-19 above was the package's `modified` time, when 1.0.64 was published under the `alpha` tag. The public source is a monorepo snapshot at **1.0.45, 2026-09-29**; seventeen releases since have no published source, and the npm tarball holds a bootstrap and per-platform binaries, no source. **What can be known**: the design as of 1.0.45 (default `true`, trust gate, the skip key), the live reference's "default `true`", and that no changelog entry from 1.0.1 to 1.0.64 announces a change to it (two mention `.envrc`: 1.0.1 fixed a session freeze on `.envrc` evaluation; 1.0.47 made sessions with an `.envrc` start faster). **What cannot**: that the 1.0.62 binary behaves as the 1.0.45 source reads; only a run shows that, which is Glazier's to pose.

### C4. Codex, filesystem denials at `rust-v0.163.0` (new; not in the text above)

Both of Sounder's statements hold, with one addition for macOS.

- **Where deny-read lives.** Only the beta permission profiles deny reads: `[permissions.<name>.filesystem]` entries with `"deny"` ("Use `"deny"` to deny reads for matching paths"), scoped `":workspace_roots"` entries, and `glob_scan_max_depth` (default none; `codex-rs/config/src/permissions_toml.rs` L224–231). The legacy `sandbox_mode` and `[sandbox_workspace_write]` keys have no read-deny at all. The Permissions page opens with "Beta. Permission profiles are under active development and may change."
- **Superseded by the older settings.** "If `sandbox_mode` appears in any loaded config file, you pass `--sandbox`, or the selected config profile sets `sandbox_mode`, Codex uses those older sandbox settings instead of `default_permissions`" (the Permissions page), and the code agrees: `resolve_permission_config_syntax` (`codex-rs/core/src/config/mod.rs` L2627–2672) returns the legacy syntax on a `--sandbox` override, otherwise whichever of `sandbox_mode` or `default_permissions` the highest config layer sets; the one managed exception is `allowed_permission_profiles`. Superseded means not merged: the `[permissions]` deny entries are then not applied. The chapter's "reconcile them before relying on these rules" is right.
- **Collected per sandboxed process on Linux, WSL and supported Windows.** Bubblewrap "can only mask concrete paths", so deny-read globs are expanded before the sandbox is built (`codex-rs/linux-sandbox/src/bwrap.rs` L500–517, with `rg --files --hidden --no-ignore --glob` or an internal walker, capped by `glob_scan_max_depth`) and the matches masked with `/dev/null` mounts; WSL2 is the same path, WSL1 unsupported; Landlock carries no deny-read at this tag. Windows MXC and elevated backends snapshot glob matches into deny ACEs (`codex-rs/windows-sandbox-rs/src/deny_read_resolver.rs` L29–35; exact, non-glob paths that do not exist are pre-created so they cannot be created and then read); the unelevated backend refuses deny-read policies outright. The documentation says the same: "deny-read glob matches are enumerated when each sandboxed process starts. Matching files created afterward are not added to that process's deny list". A file keyhole writes while a long-lived shell, watcher or dev server runs under Codex is readable by that process until it is restarted; a new sandboxed process re-enumerates.
- **macOS is different, in the safe direction.** Seatbelt profiles compile each glob into `(deny file-read* (regex …))` rules evaluated by the kernel at access time (`codex-rs/sandboxing/src/seatbelt.rs` L624–662), and a regression test creates a matching file *after* the sandbox launched and asserts it is denied (`codex-rs/exec/tests/suite/seatbelt.rs` L473–525 *[amended below, C4a: that test covers writes; the read test is L717–755]*). So on macOS a `.env` created after the process started is covered; the chapter's sentence correctly lists only Linux, WSL and Windows, and can say that macOS covers later files. The non-macOS startup warning for unbounded `**` ("set `glob_scan_max_depth` … or enumerate explicit depths") also holds.
- **C4a, amended 2026-10-20 (evening), on Sounder 6's catch.** The test cited above, `seatbelt_deny_globs_block_writes_to_existing_and_new_files` (L473–525), exercises overwrite, truncate and unlink on a file created after policy generation; it asserts nothing about reads. The read case has its own test in the same file: `seatbelt_protects_directory_trees_created_after_policy_application` (L717–755) applies a `**/*.env` deny, then, in a closure run *after* the sandbox is up, creates `late/deep/secret.env` and runs `/bin/cat` on it, asserting failure ("Seatbelt allowed read after protected directory appeared"), with the `assert_denied_read` helper (L198–210) also checking that nothing leaked to stdout. So "on macOS a later-created `.env` is covered for reads" rests on the rule generation *and* on that test, not on the one first cited. The claim stands; the citation was wrong.
- One more line from the source: Codex's own in-process file tools "still evaluate the original patterns directly at read time" (`bwrap.rs` L502), so the snapshot gap is a shell-subprocess gap, exactly the case the documentation names.

### What this changes above

The TL;DR table's Gemini column: "Project `.env` loaded by the harness itself" now reads "yes: the first `.env` found walking up to the filesystem root, `.gemini/.env` first at each level when trusted, then `~/.gemini/.env` and `~/.env`"; "Project file honored before the folder is trusted" now reads "settings: no; `.env`: yes, four authentication names, values stripped". The Grok column: "`.envrc` in the working directory, on by default (`load_envrc`), only when the folder is trusted". The source line: 1.0.62 published 2026-10-16. Nothing in the five design consequences changes; C2 adds one line to the probe, and C3 adds "on by default" to the `.envrc` doubt, which makes it sharper, not weaker.
