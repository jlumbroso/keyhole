## 1. Claude Code

**Consumers and scope.** The settings `env` block (user, project, local, managed, `--settings`) is "for every session and for the subprocesses Claude Code starts from it" and "reach[es] every subprocess Claude Code starts" (settings reference, `env`); the subprocesses the environment-variables page names are "Bash commands, hooks, and stdio MCP servers". A server entry's own `env` (`.mcp.json` `mcpServers.<name>.env`, or the local and user entries in `~/.claude.json`) is "environment variables passed to the server"; `headers` are "for HTTP server authentication"; `headersHelper` runs a command at each connection for HTTP headers only ("can't return env for stdio").

**The probe** (`scripts/ephemeral/2026-10-24-claude-mcp-env-probe.sh`, Claude Code 2.1.304, a throwaway project, no API call): a stdio "server" that only dumps its environment, registered at local scope so no approval was needed, with the variable given through `claude --settings <file>`, the settings `env` mechanism outside any repository file. Result: the server's environment held the variable with the settings value; the argument `${KEYHOLE_PROBE_TOKEN:-UNSET-IN-EXPANSION}` arrived **expanded to the value**; the server's working directory was the project folder and `CLAUDE_PROJECT_DIR` named it. So a settings `env` value reaches a stdio server both ways: as its process environment and as the source of `${NAME}` expansion in `.mcp.json`. The documentation implies both ("Claude Code writes each `env` entry into the process environment"; `${VAR}` "expands to the value of environment variable `VAR`") without stating them together.

**Literal or reference.** The committed `.mcp.json` can hold only `"${NEON_API_KEY}"` (in `env`, `args`, `url` or `headers`), with the literal in `.claude/settings.local.json` `env`; for a stdio server that reads its variable by the same name, the entry needs nothing at all, because the settings value is already in its environment. One exception for remote servers: in a remote server's `url` and `headers`, "Claude Code reads credential variables from your environment as empty rather than expanding them", for a set it does not enumerate (its own credentials, cloud providers' credentials, `HTTPS_PROXY`, `NPM_TOKEN`, …), while "a name outside this set, such as `API_KEY`, expands as written". `RENDER_API_KEY` and `NEON_API_KEY` are not named; the first real header is the check.

**Merge and precedence.** Settings: managed, then `--settings`, then `.claude/settings.local.json`, then `.claude/settings.json`, then `~/.claude/settings.json`; "when more than one settings file sets a variable, the highest-precedence one applies", per variable. Servers: "the entire server entry from that source is used; fields are not merged across scopes", local scope (the `~/.claude.json` entry under the project path) over project `.mcp.json` over user scope.

**Protection.** Claude Code ignores `settings.local.json` in git only when it creates the file ("if you create it by hand, add it to `.gitignore` yourself"), and the rule it writes goes to the **global** excludes file. If the file is tracked, "Claude Code treats it as repository-supplied instead and holds its rules until you trust the folder." No warning about a tracked file is documented. So Keyhole's two git checks (tracked first, then ignored) apply to this file exactly as to `.env`. Trust gates everything project-side: `env` "from project and local settings: after you trust the workspace"; approvals of `.mcp.json` servers written to `settings.local.json` are "ignored in an untrusted folder, and the server stays at ⏸ Pending approval", which the probe showed.

**Reload.** A saved change to settings `env` applies to the running session ("again in the running session when a saved change alters the merged `env`"), but a server already running keeps the environment it was started with; whether `.mcp.json` edits are detected is not documented. The documented remedy is `/mcp`, "select **Reconnect** from the server's menu", or `/mcp reconnect all` (2.1.284+), or a restart.

## 2. Codex CLI, `rust-v0.164.0`

- **Stdio.** The child's environment is built from scratch: `DEFAULT_ENV_VARS` (`HOME`, `LOGNAME`, `PATH`, `SHELL`, `USER`, `LANG`, `TMPDIR`, `TZ`, …) plus the names in `env_vars`, each read from Codex's own process environment, plus the literals in `env` (`rmcp-client/src/utils.rs`, `create_env_for_mcp_server`; applied with `Command::envs` in `stdio_server_launcher.rs` L276). `shell_environment_policy.set` governs "spawning a process via shell-like tools" and is never consulted by the MCP launcher; nothing sets Codex's own environment from config. So a name-only `env_vars = ["NEON_API_KEY"]` works only if the shell that launched Codex exported the value; `.env` is not loaded by Codex (removed in 0.30.0).
- **HTTP.** `bearer_token_env_var` ("The actual secret value must be provided via the environment"), `env_http_headers` (header name → variable name), `http_headers` (literals), `http_headers_helper` (a command printing headers); a literal `bearer_token` fails to load: "uses unsupported `bearer_token`; set `bearer_token_env_var`".
- **Files.** `~/.codex/config.toml` (user) and `.codex/config.toml` in a trusted project, "closest file to your working directory wins", merged recursively key by key, project over user; `mcp_servers` is not on the project denylist. No `${VAR}` expansion in config values at this tag either (the `--oauth-client-secret "$X"` example is the shell's expansion at `codex mcp add` time, writing a literal).
- **Reload.** Servers start with the session; `Op::RefreshMcpServers` exists in the protocol but nothing in the TUI or app server sends it, and `/mcp` only lists and logs in. A configuration change needs a restart of Codex.
- **For Keyhole**: the only private place for a literal is the home file `~/.codex/config.toml` (`[mcp_servers.<id>.env]`), outside the project and outside git, which ADR-0010 says needs its own consent story; a project `.codex/config.toml` is a committed file.

## 3. Gemini CLI, `v0.65.0`

- **Stdio.** A stdio server is refused in an untrusted folder. Otherwise the child gets Gemini's environment after **forced** redaction (`enableEnvironmentVariableRedaction: true` at spawn, whatever the setting says): names matching `/TOKEN/i`, `/SECRET/i`, `/PASSWORD/i`, `/KEY/i`, `/AUTH/i`, `/CREDENTIAL/i`, `/PRIVATE/i`, `/CERT/i`, a fixed list such as `DATABASE_URL`, and token-shaped values are removed, unless the name is in `security.environmentVariableRedaction.allowed` or starts with `GEMINI_CLI_`. Then the entry's `env` is added, each value expanded with `$VAR` **against the redacted environment** (`mcp-client.ts` ~L2342–2392; the test "should use a sanitized environment for variable expansion to prevent secret leaks"). Literals in `env` pass intact (the test "should expand … and not redact them").
- **The `.env` route, read not run.** Settings values are also `$VAR`-resolved once at load, from `process.env`, with the placeholder kept when the variable is unset; and that happens **before** `loadEnvironment` reads `.env` into `process.env` (`settings.ts`, resolution ~L819, `.env` at ~L984). So `"env": { "NEON_API_KEY": "$NEON_API_KEY" }` with the literal only in `.env` reaches spawn time as a placeholder, is expanded against the redacted environment, and **becomes empty**, because the name matches `/KEY/`. It works if `NEON_API_KEY` is listed under `security.environmentVariableRedaction.allowed`, or if the variable is exported before Gemini starts. This is a code-path reading; a two-minute live check settles it.
- **HTTP.** `headers` with `$VAR`, the same redacted expansion; OAuth with discovery, `/mcp auth <name>`; Google credential providers.
- **Files and trust.** `~/.gemini/settings.json` and `.gemini/settings.json`; `mcpServers` is shallow-merged per server name, project over user; the project file is dropped entirely when untrusted.
- **Reload.** `/mcp reload` (alias `refresh`) restarts the servers from the configuration already in memory; it does not re-read `settings.json`, and nothing watches it or `.env`. A changed value needs a restart of Gemini.
- **For Keyhole**: `.env` (its first target) plus a name-only `"$NEON_API_KEY"` in the committed `.gemini/settings.json` **and** `"security": { "environmentVariableRedaction": { "allowed": ["NEON_API_KEY"] } }`, then restart Gemini. Without the allow-list line the server silently gets an empty value.

## 4. Grok Build, `2bdd1d6a`

- **Stdio.** The child inherits Grok's full environment (no `env_clear`), with the entry's `env` layered on top and `GROK_SESSION_ID` added (`xai-grok-mcp/src/servers.rs` L4771–4778, L4870–4874). `${VAR}` and `${VAR:-default}` are expanded **at load time from Grok's process environment** in `command`, `args`, `env`, `url`, `headers` and `bearer_token_file` (`xai-grok-config/src/loader.rs` L590–594; the guide: "To avoid putting secrets in the config file, reference an environment variable with `${VAR}`").
- **What does not reach MCP.** `.envrc` variables (`session.load_envrc`, on by default) are collected into a map and handed to the bash tool only; so is the `env` Grok reads from Claude Code's `.claude/settings.json` and `settings.local.json` (`claude_settings.rs` L405–411: merged "cwd highest, `settings.local.json` over `settings.json`", project-tree values dropped unless trusted). Both land in `session_env`, consumed by the bash tool and the terminal run request, never by `xai-grok-mcp` and never by `${VAR}` expansion, which reads `std::env::var`. The source comment "injected into every spawned subprocess" overstates it.
- **HTTP.** `headers = { Authorization = "Bearer ${X}" }`; `bearer_token_env_var`; **`bearer_token_file`**: "Grok reads the file on every request to the server and sends `Authorization: Bearer <contents>`, with surrounding whitespace trimmed, so a rotated token takes effect on the next request without restarting Grok or reconnecting the server"; absolute or `~/` path, may use `${VAR}`; replaces an `Authorization` header or `bearer_token_env_var`; the live reference omits it, the pinned guide has it.
- **Files, precedence, trust.** `~/.grok/config.toml` < `<repo-root>/.grok/config.toml` < `<cwd>/.grok/config.toml`; a same-named server "replaces it entirely (fields are not merged)"; below `config.toml`, the compatibility sources `~/.claude.json`, `.cursor/mcp.json`, project `.mcp.json` never override. Project-declared servers, and any same-named server from any tier, are dropped until the folder is trusted.
- **Reload.** The leader process watches `~/.grok/config.toml`, `<cwd>/.grok/config.toml` and `<cwd>/.mcp.json` and reloads only the servers whose configuration changed (`config/watcher.rs` L83, L202; `servers.rs` L697 "Diff-based config update"); `/mcps` with `r` refreshes the list. One known limitation: a `<cwd>/.grok/` folder created after the session opened is not watched.
- **For Keyhole**: for an HTTP server, a file Keyhole writes (mode 0600, git-ignored) named by `bearer_token_file` is the cleanest split of all four, name-only in the config, literal in a private file, rotation without restart. For a stdio server the literal goes in the entry's `env`, in the home file or a project file.

## Across the four

- **A general environment is the MCP destination only in Claude Code.** Codex clears, Gemini redacts the very names a secret has, Grok inherits but reads neither `.envrc` nor Claude's `settings.local.json` for MCP. Sounder's warning stands and is sharper than the matrix put it: in Gemini a name-only reference to a `*KEY*` variable yields an empty string unless allow-listed.
- **Name-only references exist in all four**, in different grammars: `${NAME}` (Claude Code, Grok), `env_vars`/`bearer_token_env_var`/`env_http_headers` (Codex), `$NAME` plus the allow-list (Gemini). Only Grok has a file reference (`bearer_token_file`); only Codex rejects a literal token outright.
- **Reload is four different gestures**: reconnect from `/mcp` (Claude Code), restart Codex, restart Gemini (`/mcp reload` does not re-read files), nothing (Grok hot-reloads; a token file needs nothing at all).
- **Trust gates the project file everywhere**, and in Claude Code a tracked `settings.local.json` is itself demoted to repository-supplied. Keyhole's git checks belong to this file too.

## What this does not settle

- Gemini's `.env`-plus-`$VAR`-plus-allow-list path is a reading of two expansion passes; a live run with a dummy value would confirm the empty-string outcome and the fix.
- Claude Code's set of "credential variables" read as empty in remote `url` and `headers` is not enumerated; the first real header is the test.
- Whether Claude Code detects a `.mcp.json` edit without a reconnect; not documented, and the reconnect is cheap.
