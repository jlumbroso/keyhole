# Two reading items for the append decision: duplicate names in `.env` loaders, and comments in `settings.local.json`

- **Date**: 2026-10-20
- **By**: Surveyor 5.1 (Claude Fable 5.1); read from each loader's source, plus one run of `claude doctor` on a throwaway project
- **For**: ADR-0001's Decision, principle 3 ("Edits are additive. Append where the format allows … each change carries a standard comment"), and its two action items for me
- **Sources**: `motdotla/dotenv` 18.0.8 (master, 2026-10-16); `theskumar/python-dotenv` 1.2.4 (main, 2026-10-01); `compose-spec/compose-spec` and `compose-spec/compose-go` (main, 2026-10-14); `direnv/direnv` (master, 2026-10-12); `google-gemini/gemini-cli` 0.66.0-nightly (main, 2026-10-19, pinned to `dotenv@17.1.0`); Claude Code's documentation (`code.claude.com/docs/en/settings`, `settings-example`, `debug-your-config`) and Claude Code native 2.1.304 through `scripts/ephemeral/2026-10-20-claude-settings-comments-probe.sh`. Quotes are the sources' wording; line numbers are from the commits named.

## TL;DR

1. **Appending to `.env` is safe as the default.** Every one of the five loaders resolves a name that appears twice in one file to the **last** line, by plain map assignment, and **none warns**. The one thing a later line cannot beat is a variable already exported in the process environment, under three of the five loaders; keyhole's probe principle already covers that.
2. **Claude Code's settings files take no comments.** The documentation says "strict JSON: a `//` comment or a trailing comma is a syntax error", and Claude Code 2.1.304 marks such a file "Invalid or malformed JSON", after which the **whole file**, every `env` value in it, is out of effect: a dialog at an interactive start, silently skipped in `-p` mode. keyhole's standard comment lives in its log only.

## 1. A name that appears twice

| Loader | Same name twice in one file | Warns? | A variable already in the process environment | Appending `NAME=new` to a file that has `NAME` |
| --- | --- | --- | --- | --- |
| Node `dotenv` | last wins: `obj[key] = value` in the parse loop (`lib/main.js` L30–53, and the fast parser L238) | no, not even with `debug` | `config()`: the environment wins unless `override: true` (`populate`, L374–391); README L498: "we will never modify any environment variables that have already been set" | the file says `new`; the process sees `new` only if `NAME` was not already set, or `override` is on |
| `python-dotenv` | last wins: `OrderedDict(raw_values)` / `new_values[name] = result` (`main.py` L79–92, L333–355) | no (only "could not parse statement" for malformed lines) | `load_dotenv(override=False)` by default: the environment wins; `dotenv_values()` returns the file's value regardless | same as `dotenv`; and `set_key` **rewrites in place**, replacing every line with that key (`main.py` L271–282), so a tool using it after keyhole turns both lines into the new value |
| Docker Compose `env_file` | last wins: `out[key] = value` into one map (`compose-go` `dotenv/parser.go` L33–67); the spec is silent on it | no | the host environment never overrides an explicit `env_file` value; only the service's `environment:` does (`OverrideBy`); across several files "the value from the last file in the list stands" (`container_spec.md`) | `new` |
| direnv `dotenv`, and `source .env` | last wins: `dotenv[key] = value` (`pkg/dotenv/parse.go` L150–171); a shell assigns top to bottom | no | the file **always** overrides: `.envrc` evaluates `export KEY=value` for every key (`stdlib.sh` L234–250) | `new`, overriding anything set before. | Gemini CLI | last wins: it calls `dotenv.parse`, which has already collapsed duplicates (`packages/cli/src/config/settings.ts` L729–765) | no; the loader's `catch {}` swallows even read errors | the environment wins, with no override option: `if (!Object.hasOwn(process.env, key)) process.env[key] = value`; exactly one file is loaded, never merged (`findEnvFile`, L594–632) | the process sees `new` only if `NAME` was not already set |

**What this means for principle 3.**

- **Append is the right default**, and the comment "this line overrides the one above" is true under every loader read. No loader documents duplicate handling; all five inherit "last assignment wins" from their parser, so the claim is from source, not from a promise, and a future parser could change it. A small test fixture in keyhole (a file with the name twice, parsed by `dotenv` from `node_modules`) would catch the one loader keyhole can run.
- **The process environment, not the file, is the real collision**, under `dotenv`, `python-dotenv` and Gemini CLI: a `NAME` exported in the shell beats both lines in the file. The probe keyhole runs "before and after every change" should include the extension host's own environment and say "set in your shell; the file's value will not be used by loaders that respect the environment" when it is. Under direnv and `source`, the file wins instead; the log line can name which.
- **`set_key` is the one writer that rewrites instead of appending**, and it rewrites every matching line; a file keyhole appended to stays consistent after it.

## 2. Comments in `settings.local.json`

- **Documentation**: "Settings files are strict JSON: a `//` comment or a trailing comma is a syntax error, and Claude Code reports the file as a Settings Error at the next start" (`settings`); the example page keeps its commented copy in a separate tab "because Claude Code doesn't accept comments in a settings file" (`settings-example`). Block comments are not named; "strict JSON" covers them.
- **Ran**: with a `//` and a `/* */` comment in `.claude/settings.local.json` of a throwaway project, `claude doctor` (native 2.1.304, darwin-arm64) prints "Invalid settings … settings.local.json: Invalid or malformed JSON"; the strict copy prints no such section.
- **What happens next**: "At the start of an interactive session Claude Code shows a dialog that lets you fix the file with Claude's help, exit, or continue without the broken settings"; "A `-p` run shows no dialog … Claude Code skips the broken file or values and continues". A Settings *Warning* (one bad entry, the rest kept) is for malformed rules and unknown hook names, not for a syntax error. So one comment switches off every variable in the file, and in print mode nobody is told until `claude doctor` is run.
- **Claude Code rewrites the file itself**: a standing permission approval "saves that approval as an `allow` rule in `.claude/settings.local.json`", and some `/config` options save there. Whether a rewrite preserves unknown keys, order or formatting is not documented; keyhole should re-read before every write (which the probe principle already implies) and not expect its layout to survive. The documented editor-help route is a `$schema` key, which is a known key and harmless.

**What this means for principle 3.** The format-preserving editor (`jsonc-parser` `modify`) is still the right tool, because it keeps whatever the person has, but keyhole must never *add* a comment to this file. The standard comment (who, version, when, why, whether it overrides) goes into keyhole's log; the file gets the value and nothing else. The same rule holds for any harness file that is strict JSON; Codex's and Grok Build's TOML accept `#` comments, and `.env` accepts them, so the comment can travel there.
