# Accessible entry: four things read in VS Code's source

- **Date**: 2026-10-20 (evening)
- **By**: Surveyor 5.1 (Claude Fable 5.1), read not run
- **For**: Glazier's brief `2026-10-20-2324-glazier-to-surveyor-accessible-entry-source-reads.md`; ADR-0003 (QST-SHOW-VALUE, the entry tab, conformance)
- **Source**: VS Code at tags `1.134.0` (the floor) and `1.141.0`, the local clone at `~/Programming/_vscode-source/vscode`; paths under `src/`. Line numbers are at `1.141.0`; every file was compared by blob id with `1.134.0`, and the differences are named where they exist. Nothing here was run.

## TL;DR

| Question | Answer |
| --- | --- |
| 1. Flip `password` on an open `createInputBox()` box | **Yes, live, value kept**: the setter travels to the shown box and flips the native input's `type`; the value stays in the field. An eye button with `eye` / `eye-closed` codicons works through `buttons` and `onDidTriggerButton`, and its icon is swapped by reassigning `buttons`. `ignoreFocusOut` is the same code path as `showInputBox`. Same at both tags |
| 2. What a screen reader hears | A native `<input type="password">` with an `aria-label` built from the placeholder and title; VS Code announces nothing per keystroke in a quick input; what it does announce is the validation message, so that text must never carry the value. Whether a keystroke is read as "bullet" or silence is the browser's and the screen reader's, not VS Code's: a hand check |
| 3. Hot exit and untitled editors | **An untitled editor's text is written to disk in plain UTF-8 about one second after each pause in typing, whatever `files.hotExit` says**; the setting governs only shutdown. No extension can exclude an editable text document. The evidence for "the tab must be a webview" is complete |
| 4. What a webview's content is visible to | Its DOM is cross-origin to the workbench, unreachable by other extensions (no API) and by chat tools; the integrated browser's screenshot tool captures only the browser page. Two exposures remain: the user-triggered **Screenshot Window** chat attachment captures the whole window's pixels, panel and quick input included; and every keystroke in a webview is re-dispatched to the workbench keybinding service in memory. `setState` lands in the workspace's `state.vscdb` on the 60-second idle flush or shutdown, only if a serializer is registered: never `setState` a secret. `postMessage` is unlogged except under the developer RPC flag |

## 1. Flipping `password` on an open box, buttons, `ignoreFocusOut`

The seven files involved are byte-identical at the two tags except `quickInputController.ts` (the blur handler is at L348–351 at 1.134.0 and L350–353 at 1.141.0, same text) and `base/browser/ui/inputbox/inputBox.ts` (a resize-observer disposal change, nothing about password or aria).

- **The flip.** `api/common/extHostQuickOpen.ts` L710: `set password` stores the flag and calls `update({ password })`; `api/browser/mainThreadQuickOpen.ts` `$createOrUpdate` applies each changed parameter to the live input; `platform/quickinput/browser/quickInput.ts` `InputBox.update()` L1307–1308: `if (this.ui.inputBox.password !== this.password) this.ui.inputBox.password = this.password`; `quickInputBox.ts` L93–95: `this.findInput.inputBox.inputElement.type = password ? 'password' : 'text'`. The same `update()` writes the value only when it differs (L1297–1299), so the box's text is not touched by the flip. Keeping the value and the caret across a `type` change between `text` and `password` is the browser's behavior (both are text-entry modes that support selection, so the HTML specification keeps the selection), not VS Code's; it is the one thing in this item a hand check should confirm.
- **The eye button.** `extHostQuickOpen.ts` L393 `set buttons` → update; `mainThreadQuickOpen.ts` L221–231 expands each button's icon path and assigns `input.buttons`; `quickInput.ts` L286–314 marks `buttonsUpdated`, L418–419 re-renders the title-bar buttons on the next `update()`. `onDidTriggerButton` is `extHostQuickOpen.ts` L413 (fired at L443). The codicons exist: `base/common/codiconsLibrary.ts` L51 `eye`, L222 `eye-closed`, so `new ThemeIcon('eye')` and `new ThemeIcon('eye-closed')` are valid `iconPath`s. Toggling the icon is reassigning `buttons` with the other icon; the box stays open.
- **`ignoreFocusOut`.** `extHostQuickOpen.ts` L353 → `quickInput.ts` L263–265 → the controller's single blur handler (L350–353: hide on blur unless the flag is set), the same path `showInputBox` uses. Note `extHostQuickOpen.ts` L280: a `createInputBox()` box defaults `ignoreFocusOut` to `true`, the opposite of `showInputBox`'s default.
- **Live text under the box (option B).** `quickInput.ts` L1249–1253: `set prompt` rebuilds the message line ("<prompt> (Press 'Enter' to confirm or 'Escape' to cancel)") and re-renders; `validationMessage` takes the same line with a severity. `onDidChangeValue` (`extHostQuickOpen.ts` L385, fired at L434) delivers each keystroke's full value to the extension host. So a line such as "40 characters, ends in …f9c2" can follow typing. Two cautions: that line is announced by screen readers (section 2), and the value arrives in the extension host on every keystroke, where `Secret` discipline must already apply.
- **One exposure for option A, from section 4.** While `password` is `false`, the field renders the value in plain text, and the user-triggered **Screenshot Window** chat attachment captures the whole window's pixels. Masked, the capture shows bullets. The eye button should therefore re-mask on blur, on hide and after a short time, and the person should know a screenshot taken while revealed would carry the value.

## 2. What a screen reader hears in a password box

- The control is a native `<input>` (`quickInputBox.ts`); VS Code sets no explicit role ("the input element already has that implicit role", L41–42) and no `aria-haspopup` or `aria-autocomplete` unless a list is active. With `password`, its `type` is `password`, so assistive technology sees a secure text field.
- **Label**: `quickInput.ts` L1310–1325 composes `aria-label` as the placeholder, or "placeholder - title", or the title, else `input`; applied through `quickInputBox.ts` L125 and `inputBox.ts` L270–276. So the prompt a person hears when the box takes focus is whatever keyhole puts in `placeholder` and `title`.
- **Per keystroke, VS Code says nothing.** The two places `inputBox.ts` announces the field's value (`aria.status(this.value)`, L814 and L829) are history navigation (`showNextValue`, `showPreviousValue`), which the quick input never calls (no caller in `quickInputBox.ts` or the controller). What a screen reader says for a typed character in a password field ("bullet", nothing, or the character when the user enabled that) is the browser's and the screen reader's behavior, outside this source; it is a hand check with a screen reader on, not a reading.
- **What VS Code does announce**: the validation message, through `aria.alert` (`inputBox.ts` L538–548), and the message line's text is also what sighted users see. Anything keyhole writes there is read aloud, so option B's live line must carry only what QST-KEYPRINT-LEGIBLE allows, and never the value.
- Identical at 1.134.0 (`quickInputBox.ts` and `quickInput.ts` same blobs; `inputBox.ts` differs only in the resize-observer lines).

## 3. Hot exit, and why an untitled editor cannot hold a secret

Every backup file is byte-identical at the two tags; only `contrib/files/browser/files.contribution.ts` differs, in two unrelated lines, and the `files.hotExit` schema sits at the same lines (L123–147, registered L321).

- **The setting is about shutdown, not about writing.** Its description: "controls whether unsaved files are remembered between sessions, allowing the save prompt when exiting the editor to be skipped"; default `onExit` on the desktop (`files.contribution.ts` L128). The only readers of the setting are the shutdown paths: `services/workingCopy/electron-browser/workingCopyBackupTracker.ts` L162–165 (`if (!isHotExitEnabled) return []` before backing up at shutdown) and the browser tracker L44–46. The main process consults it only to decide which windows to restore (`platform/backup/electron-main/backupMainService.ts` L69–91); it registers every window's backup folder regardless (`windowsMainService.ts` L1698–1722).
- **Backups are continuous.** `services/workingCopy/common/workingCopyBackupTracker.ts` L148–167: every content change of a modified working copy schedules a backup; L84–94 the delay is 1000 ms (2000 ms when auto-save is on); L225–238 untitled copies always get 1000 ms, "auto-save is never on for untitled working copies". When the timer fires, L189–197 take the copy's snapshot and write it through the backup service. An untitled document created with content is modified from birth (`untitledTextEditorModel.ts` L157) and is backed up one second after creation (tracker L109–118), before any keystroke.
- **Where and what.** `common/workingCopyBackupService.ts` L516–518: `<backup home>/<window id>/untitled/<hash of the resource path>`, under `<user data>/Backups` (`environmentMainService.ts` L49). L260–294: one header line (`untitled:Untitled-1 {"typeId":""}`), then the raw UTF-8 text, written with `fileService.writeFile`: plain text, no compression, no encryption.
- **No opt-out for an editable document.** `common/workingCopy.ts`: capabilities are `None`, `Untitled`, `Scratchpad` (L17–31); `backup()` is mandatory (L194–204, "The workbench may call this method often after it receives the `onDidChangeContent` event"); `backupDelay` (L185–192) only tunes the timer; a `Scratchpad` is backed up more eagerly at shutdown, not less. `workspace.openTextDocument({ content })` creates an ordinary untitled model (`mainThreadDocuments.ts` L273–307). The only documents that are not working copies are read-only `TextDocumentContentProvider` documents (no `registerWorkingCopy` anywhere in that path), which cannot be typed into. A custom editor can own what its backup contains (`backupCustomDocument`), not whether one exists. The single environment where nothing reaches disk is an extension-development window (`windowsMainService.ts` L1694–1698: "we do not keep any backups" → the in-memory backup service, `workingCopyBackupService.ts` L135–139, L525–544), which is why a spike under F5 would not show the problem.
- **Removal.** Discarding or reverting deletes the file at once (tracker L135–146, L265–280 → `fileService.del`, L354). A normal quit with hot exit on keeps the backups so the editor is restored next launch (electron-browser tracker L125–127, L190–195). With hot exit off, the save prompt runs and Save or Don't Save then deletes them (L312, L323 → L411–445).

**So**: a secret pasted into an untitled editor is on disk in clear text within a second, under the user's data folder, and survives a quit by default. An editable text editor is not a surface keyhole can use; the entry tab must be a webview (section 4), or an input box.

## 4. What a webview's content is visible to

`webviewElement.ts` differs between the tags only in resource-stream lifecycle lines and an error message; `pre/index.html`, `mainThreadWebviews.ts`, `extHostWebview.ts` and `webviewEditorInput.ts` are identical; `mainThreadWebviewPanels.ts` adds one unrelated method at 1.141.0.

- **Isolation.** The panel is an iframe (`contrib/webview/browser/webviewElement.ts` L415–425, sandboxed) at origin `vscode-webview://<sha256 of the parent origin and the webview's own origin>` (L466–477; the desktop endpoint, `services/environment/electron-browser/environmentService.ts` L112), distinct from the workbench's `vscode-file://vscode-app`. Inside, VS Code's host page writes the extension's HTML into an inner sandboxed iframe with `document.write` (`pre/index.html` L1019–1065); it never has a URL and never passes through the service worker. The host page checks the parent's origin hash before talking to it (L326–361). Workbench and iframe speak only over a `MessagePort` with named channels (`webviewElement.ts` L507–544); no code path reads the iframe's document (`contentWindow` is used once, to focus, L972). The main process refuses `vscode-webview://…/index.html` requests from anywhere but an editor window's frame (`code/electron-main/app.ts` L403–431).
- **Other extensions.** No API returns a webview's content: `vscode.d.ts` L9964–9965 ("Webviews are sandboxed from normal extension process, so all communication with the webview must use message passing"); `html` (L9984) returns the string the owner set. Grep for screenshot, capture, `innerText` or `getHtml` across `vscode-dts/`: nothing, at both tags. Webviews live in a per-host private map keyed by an opaque handle (`extHostWebview.ts` L196), and `$onMessage` (L218–226) fires only the owner's emitter.
- **Chat and AI features.** The integrated browser's **Screenshot Page** tool (`contrib/browserView/electron-browser/tools/screenshotBrowserTool.ts` L169–200) captures the browser view's own web contents (`platform/browserView/electron-main/browserView.ts` L830–864, `this._view.webContents.capturePage`), not the VS Code window; a webview panel or a quick input is not in that surface. The one capture of the whole window is the user-triggered **Screenshot Window** item in chat's Add Context picker (`contrib/chat/browser/actions/chatContext.ts` L446–462, Electron only, vision models only) → `hostService.getScreenshot()` → `nativeHostMainService.ts` L910–915, `webContents.capturePage` of the window as a JPEG: a visible panel and a visible quick input are in the pixels, nothing is blanked. No agent tool calls it (no caller passes `attachScreenshot`, `chatActions.ts` L297–301), and it is not exposed to extensions. The browser view also captures itself every second for a placeholder image (`webContentsViewHost.ts` L208–235), the browser page only, in memory.
- **Keystrokes.** `pre/index.html` L609–621 posts `did-keydown` for every key pressed in the inner frame (key, code, modifiers; not the field's value); `webviewElement.ts` L254–256, L721–733 rebuilds a `KeyboardEvent` and dispatches it to the workbench keybinding service, gated on the webview being the active element and the event being trusted (L713–715, L722). A secret typed into a webview input is re-emitted key by key to the workbench DOM, in memory, with no logging found on that path. It is how keybindings work inside webviews; it is also why the tab's input should not be the focused element longer than needed, and why nothing in keyhole may install a keydown listener on the workbench side.
- **`setState` / `retainContextWhenHidden`.** `setState` posts `do-update-state` (`pre/index.html` L228–233), held in memory on the overlay (`overlayWebview.ts` L293–296, L335). It reaches disk only through the editor part's memento: `webviewEditorInputSerializer.ts` L107–115 includes `state` when the panel can be serialized (L56–58 → `webviewWorkbenchService.ts` L365–371: only if the extension registered a `WebviewPanelSerializer`, `mainThreadWebviewPanels.ts` L244); `editorPart.ts` L102, L156, L1485–1492 writes the workspace-scoped memento; the storage flushes on the 60-second idle (`platform/storage/common/storage.ts` L330, L359–367) and at shutdown (L638), into `<user data>/User/workspaceStorage/<workspace id>/state.vscdb` (`storageMain.ts` L415–420), a SQLite file, key `editorpart.state`, state as a JSON string. `retainContextWhenHidden` keeps the live iframe in memory with `visibility: hidden` (`overlayWebview.ts` L187–198); without it the iframe is destroyed on hide. **Rule for keyhole**: never pass a value or anything derived from it to `setState`, and do not register a serializer for the entry tab unless its state is empty.
- **`postMessage` logging.** `mainThreadWebviews.ts` L66–82 and `extHostWebview.ts` L129–134, L218–226 carry messages with no log, trace or console call; `webviewElement.ts` logs only "webview ready" and "will update content" without payloads (L524, L645, L671). The only place a message's payload is printed is the extension-host RPC logger under `--logExtensionHostCommunication` (`extensionHostManager.ts` L252, L514–527), the same developer flag noted for the input box; the telemetry variant logs lengths only (L562, L583).
- **Disk.** The panel's HTML is never fetched by URL, so neither the service worker nor Chromium's cache sees it; resources loaded through `asWebviewUri` can be cached by Chromium's Cache Storage when the host returns an etag (`pre/service-worker.js` L443, L519–529), which is the browser engine's store under the user-data folder, not VS Code code. Keep the entry tab's assets static and never put a value in a resource URL.

## Consequences for QST-SHOW-VALUE and the tab

- **A (eye button on the box)**: the API allows it in full at the floor; the value is in the extension host on every keystroke either way, and while revealed it is in the window's pixels for a user-triggered screenshot. Re-mask on blur, hide and a timer.
- **B (live length and ends under the box)**: allowed through `prompt` or `validationMessage` driven by `onDidChangeValue`; the line is announced by screen readers, so it is also the accessible form of "what did I type", provided it carries only what QST-KEYPRINT-LEGIBLE permits.
- **C (only in the tab)**: a webview can do both, with its own control; it is the only editable surface that never touches disk by VS Code's doing (section 3), at the cost of the keystroke forwarding and the screenshot exposure, which are the same as the box's.
- **Not an option**: any text editor, untitled or file-backed, for entry (section 3).

## What a hand check must still cover

- The caret and value across the `password` flip (browser behavior, section 1).
- What VoiceOver and NVDA say per keystroke in the masked box, and that the message line, not the value, is what is read (section 2).
- That a webview input's value does not appear anywhere after a window reload with a serializer registered but empty state (section 4), which is the one path where a mistake would persist.
